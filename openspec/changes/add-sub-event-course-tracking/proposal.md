# 变更提案：子事件与疗程

**change-id**：`add-sub-event-course-tracking`
**日期**：2026-09-10
**影响 spec**：`event-management`（ADDED / MODIFIED）、`status-calculation`（MODIFIED）
**影响数据**：`events` 表结构变更，数据库版本 2 → 3

---

## 为什么改

真实使用中暴露了三个场景，现有模型都答不上来：

1. **同时吃的几种药节奏不同** —— 退烧药一天 2 次、消炎药一天 3 次，
   现在只能建成两个平级事件（「吃退烧药」「吃消炎药」），
   它们属于同一次看病这件事在模型里没有载体，列表里散在各处。
2. **疗程结束后不应再被关注** —— 吃药依附于某次看病，感冒好了就该整体退场。
   现在要一个个手工归档，且归档后子事件与那次看病的关联也丢了。
3. **感冒这类看病不该有周期** —— 用户不填 `targetDays` 时，
   走 status-calculation 的三级回退：历史均值（记满 2 次后）→ 30 天兜底。
   意味着「上次感冒是半年前，平均半年一次」会被算成逾期，
   首页长期挂一个红色「该看病了」。用户从来没说要看病有周期。

根因是同一个：**事件是平表，且「有没有节奏」只有一个维度（`targetDays` 是否为空）**。
一次看病、这次开的几种药、这次药要吃几天，这三层信息被压成了一个事件。

---

## 目标

- 让「一次看病」成为可命名的容器（疗程），药作为它的子事件挂在下面，
  各自保留自己的每日频次。
- 疗程结束后一键整体退场，且随时可整体恢复。
- 让「感冒」这类没有周期的事件明确表达「按需」，不再被周期逻辑误判为逾期。

## 不做什么（明确排除）

- **不做三层层级**。看病 → 疗程 → 用药，中间那层由「新建疗程」这个动作表达，
  数据结构只保留父 → 子两层。三层会让首页排序、小组件、归档、导出的改动量翻倍，
  而收益只是多一层统计口径。
- **不做服药提醒通知**。project.md 「已确认不做」里已明确：
  用户习惯是主动打开查看，提醒是打扰。本次只让首页能回答「今天还差几次」。
- **不做自动 / 定期归档**。同上，已确认不做。
  疗程结束一律由用户手动确认，系统只提供入口。
- **不做连续天数、完成率、漏服统计**。今日进度只回答「今天」，
  不累计、不排名、不因昨天漏记而回溯惩罚（铁律 2）。
- **不做药品库 / 剂量单位**（mg、粒、饭后服用）。这是外部记忆工具，不是用药管家。
- **不改变记录的存储方式**。`records` 表不动，子事件各自记自己的记录。

---

## 用户可见的变化

| 场景 | 现在 | 改后 |
|---|---|---|
| 多种药不同频次 | 平级事件，靠名字区分 | 挂在疗程下，各自显示「今日 1/3」 |
| 感冒看病 | 记满两次后大概率变红 | 按需型，只显示「上次距今 X 天」 |
| 疗程结束 | 逐个手工归档 | 父事件一键结束，父子一起进归档，可一起恢复 |

## 兼容性

- 数据库 2 → 3 迁移：新增列取默认值，老事件行为完全不变
  （`kind` 默认 `PERIODIC`，`parentId` 与 `timesPerDay` 默认 null）。
- 备份 JSON / CSV 导出新增字段，旧备份导入时用默认值补全。
