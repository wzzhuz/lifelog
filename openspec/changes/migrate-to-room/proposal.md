# 持久化迁移到 Room（SQLite）

## 对应需求

需求 6：每次新增都要重写整个 JSON 文件，记录上万后会不会变慢？搜索是不是也慢？

## 结论先行

**你是对的。** 我上一版的判断过于保守，这里修正。

原先我主张「只修两处浪费，不换数据库」，理由是实测 1 万条单次写入
修完瓶颈后约 29ms，"感知不到"。**这个论证有个漏洞**：

> 我当时只算了「写入一次要多久」，
> 没算「数据量再涨十倍会怎样」，也没算**搜索**。

你提的两点都成立：

| 你的质疑 | 核实结果 |
|---|---|
| 「每次新增都重写整个文件」 | 确实。JSON 是全量覆盖，<br>记一笔要重排 1 万条再写盘，开销**随数据量线性增长** |
| 「搜索是不是也慢」 | 确实。原实现是**遍历所有事件的全部记录**做字符串匹配，<br>上万条时每次输入都要扫一遍全表 |

**纠正我上次的错误判断**：个人琐事记录是高频应用，
数据量增长比我预估的快得多——一天记 10 条，三年就上万。
线性增长的开销迟早会碰到，早换比晚换成本低。

## 做什么

### 1. 底层换成 Room（SQLite）

- 事件表 + 记录表，建立索引
- 写入只改变更的那一行，**与总数据量无关**
- 搜索走 SQL 查询，**只返回命中的结果**

### 2. 首页列表不再加载全部记录

这是我在改造中发现的**比换库本身收益更大的问题**：

原实现给首页每个事件都装配了完整的记录列表，
哪怕界面上只是要显示「共几次」。
换库后改用 SQL 聚合统计（数量 / 最早 / 最近），
**首页开销只与事件数有关（几十个），与记录总数无关**。

### 3. 旧数据自动迁移

首次启动自动把 `lifelog.json` 搬进数据库，
原文件改名留档（**不删除**，留后悔药），
迁移失败则下次启动重试，数据不会丢。

### 4. 在独立分支验证后再合入

按你的要求：先建 `feature/room-migration` 分支，
**编译成功、确认可用**再合入主线。主线始终是可用的版本。

## 不做什么

- ❌ 不引入 DI 框架（Hilt / Koin）—— 保持 `project.md` 的约定
- ❌ 不做云同步（违反离线原则）
- ❌ 不改数据模型字段（迁移是平迁，不是重构）
- ❌ 不做分页加载（聚合查询已经让首页与数据量无关，暂时用不上）

## 影响范围

**触及的 spec 模块**：
- `specs/data-persistence/` —— 核心改动，存储方式从 JSON 文件改为 SQLite
- `specs/record-capture/` —— 搜索行为改为 SQL 查询
- `specs/status-calculation/` —— 补充「聚合统计」的计算路径

**是否需要重新安装包**：是。**但数据会自动迁移，不需要重新录入。**

**是否会丢数据**：否。三重保险：
1. 旧 JSON 改名留档，不删除
2. 迁移失败不写完成标记，下次重试
3. 数据库自带本地备份机制

## 与项目铁律是否冲突

- [x] 不违反三条铁律
- [x] 不涉及「已确认不做」清单

**对铁律一的影响是正向的**：
记一笔从「重排全量数据」变成「插入一行」，
应用越用越快，而不是越用越慢。

## 关于 `project.md` 的一处修订

`project.md` 原本写着：

> **刻意不引入**：Room、Hilt/Koin、Coil/Glide。
> 数据量小（个人记录，千级），JSON 文件直读直写更简单可控。

**「数据量小（千级）」这个前提被证伪了**——
高频记录场景下会到万级。本 change 合入时需同步修订该条目，
改为说明「曾经用 JSON，万级数据量后迁移到 Room」，
并保留当初为什么一开始不用 Room 的理由（降低 CI 首次编译失败率），
这个取舍在那个阶段是对的。

## 验证方式

1. 分支编译通过
2. 装到手机，确认旧数据完整迁移（事件数、记录数对得上）
3. 造 1 万条测试数据，实测记一笔、搜索、进设置页的耗时
4. 确认无回退后合入主线
