# ADDED Requirements

### Requirement: 归档可恢复

系统 SHALL 提供已归档事件的查看入口，
并支持**恢复**（取消归档）与**彻底删除**。

系统 SHALL NOT 让归档成为不可逆操作。

#### Scenario: 查看与恢复

- **GIVEN** 用户归档了「洗牙」
- **WHEN** 打开设置页的已归档列表
- **THEN** 看到「洗牙」及其记录条数
- **AND** 可将其恢复回主列表

#### Scenario: 彻底删除需二次确认

- **GIVEN** 「洗牙」有 5 条记录
- **WHEN** 用户点击彻底删除
- **THEN** 弹确认框说明将连带删除 5 条记录
- **AND** 确认后才执行

#### Scenario: 归档前提示恢复路径

- **WHEN** 用户在详情页点击归档
- **THEN** 弹确认框说明「可在设置 → 已归档事件中恢复」
- **AND** 不静默执行

**理由**：归档曾只有入口没有出口——
`archivedEvents()` 已实现但 UI 层零处调用，
事件归档后无法查看、恢复或删除，唯一出路是导出 JSON 手动改字段。

#### Scenario: 归档事件计数

- **WHEN** 渲染已归档列表
- **THEN** 每个事件显示其记录条数
- **AND** 无记录的事件也出现在列表中

**理由**：列表查询 SHALL 用 LEFT JOIN 而非 INNER JOIN，
否则没有记录的事件会消失，用户再也找不回来。
显示条数是为了让用户在删除前知道会损失多少记录。

系统 SHALL NOT 因性能原因归档历史记录。

**理由**：首页走 SQL 聚合查询，开销与记录总数无关，
归档老记录对首页性能的收益为零，
却会让年度回顾需要跨表查询，反而把「看全部」变复杂。
