# 首页列表：卡片瘦身 + 拖动排序

## 对应反馈

「首页每一个事件纵向高度比较高，一个屏幕最多展示 5 个事件。
剩下的要滑动屏幕查看，事件多了不方便。而且不能拖动自定义排序，
高频事件不能放上面。」

## 核实结论：两个问题都成立，且各有一个隐藏原因

### 问题一：卡片高度——色条高度写死，与内容不匹配

`EventCard` 里色条写死 84.dp：

```kotlin
Box(modifier = Modifier.width(4.dp).height(84.dp).background(barColor))
```

但卡片实际高度由内容撑开：

```
上内边距 14
标题行（emoji + 名称 + 状态chip）  ~28
副标题（上次 / 平均 / 预计）        ~16
进度条行（含 40dp 的记一笔按钮）     40
下内边距 14
────────────────
实际约 112~126 dp
```

**色条只有 84dp，比卡片矮约 30~40dp**，下方一截没有颜色。
这是个已存在的视觉瑕疵，顺手一起修。

卡片间距 10dp，所以每条约 122~136dp，
一屏（约 700dp 可用高度）确实只能放 5~6 个。

### 问题二：自定义排序——字段早就准备好了，但从没用上

数据库里 `sortOrder` 字段一直存在，DAO 查询也按它排序：

```sql
ORDER BY isPinned DESC, sortOrder ASC, name ASC
```

**但没有任何界面能修改它。** 导入模板时按导入顺序赋一次值，
之后再也不变。

而 `ListViewModel` 的实际排序是：

```kotlin
compareByDescending { it.event.isPinned }   // 钉选优先
    .thenByDescending { it.ratio }           // 紧急度
    .thenBy { it.event.name }                // 名称
```

**完全没用 sortOrder。** 所以：
- 钉选能把事件置顶 ✅
- 但钉选的多个事件之间顺序由紧急度决定，无法手动排 ❌
- 未钉选的事件更是只能靠「紧急度 + 名称」自动排 ❌

## 做什么

### 1. 卡片瘦身（目标：一屏 8~10 个）

两种显示模式，设置页可切换：

| 模式 | 高度 | 内容 |
|---|---|---|
| **紧凑**（默认） | ~76dp | emoji + 名称 + 状态色点 + 副标题 + 记一笔按钮<br>进度条压缩为 2dp 细线贴卡片底部 |
| 舒适 | ~112dp | 保持现状布局，但修好色条高度 |

紧凑模式下：
- 进度条从独立一行改为贴底的 2dp 细线，不再占位
- 副标题缩为单行
- 「记一笔」按钮从 40dp 缩到 36dp
- 内边距 14 → 12

### 2. 修色条高度

改为 `fillMaxHeight()` 跟随卡片实际高度，
不再写死 84dp。

### 3. 拖动排序

- 长按卡片进入拖拽模式（或每张卡片加拖拽手柄）
- 用已有的 `sortOrder` 字段持久化
- 排序逻辑改为：`isPinned DESC → sortOrder ASC → name`
  （钉选仍在最前，钉选内部按手动顺序）
- 拖拽结束后批量写回数据库

**关于钉选与手动排序的关系**：建议保留钉选为「置顶层」，
手动排序决定组内顺序。这样既有置顶能力，又能精细控制。

### 4. 顺带：状态 chip 精简

紧凑模式下把「新鲜 / 快到了 / 该做了」文字 chip 
缩为一个小圆点（颜色即状态），文字在详情页看。
配合使用说明页的颜色图例，不至于看不懂。

## 不做什么

- ❌ 不做分组折叠（按标签分组可折叠）——当前事件量用不上
- ❌ 不做网格/列表布局切换——记录类应用单列更合适
- ❌ 不做自动排序规则（如「按记录频率自动置顶」）——
  手动可控比自动猜测更符合「不制造焦虑」的定位

**触及的 spec 模块**：
- `specs/event-management/` —— 新增手动排序 Requirement
- 首页卡片布局属视觉细节，不写进 spec

**是否会丢数据**：否。只是启用了一个一直存在但没用的字段。

## 与项目铁律是否冲突

- [x] 不违反三条铁律

**对铁律一的影响是正向的**：
一屏能看到的事件从 5 个增加到 8~10 个，
高频事件排在前面，记一笔的路径更短。

## 关于第三种模式：宫格 vs 分类分组

使用者提出两个候选，这里给出量化分析。

### 候选 A：宫格模式——**不建议做**

按 360dp 宽屏幕、列表可用高度约 600dp 计算：

| 布局 | 单格尺寸 | 一屏数量 | 能放下什么 |
|---|---|---|---|
| 舒适列表 | 328×122 | **5~6** | 现状，信息完整 |
| 紧凑列表 | 328×76 | **8~9** | 名字 + 上次X天 + 按钮 |
| 宫格 2 列 | 160×84 | **12** | 名字（约 6 字）+ 上次X天，字号需缩小 |
| 宫格 3 列 | 104×72 | **24** | 仅 emoji + 3~4 个字，**副标题全丢** |

**关键判断：宫格适合「看图识物」，这个应用是「读数字」。**

图库、应用列表用宫格合理，因为用户靠图标和缩略图识别。
但生活手记每张卡片的核心信息是**「距今多少天」「该不该做」**——
这是文字和数字，横向空间越窄越难读。

- 2 列：比紧凑列表多放 3~4 个，代价是字号缩小、
  长事件名截断（「结婚纪念日」+ emoji 已接近 160dp 上限）
- 3 列：数量翻倍，但「上次 12 天」这个最关键的信息没了，
  卡片退化成一个图标，失去存在意义

**结论**：2 列收益有限且损伤可读性，3 列信息量不足。不做。

### 候选 B：分类分组——**建议作为第三种模式**

按标签分组，插入**吸顶分组头**（滑动时分类名固定在顶部）。

| 项 | 说明 |
|---|---|
| 额外开销 | 每个分组头约 28dp，6 个分类 ≈ 少看 2 张卡 |
| 默认状态 | 全部展开（不增加点击层级） |
| 可折叠 | 支持，折叠后省出该组全部高度 |
| 定位 | 吸顶头让快速滑动时始终知道在哪个分类 |

**为什么是「可折叠」而不是「必须点开」**：
点开才看到事件会多一层操作，违背「一眼看到所有该做的事」。
默认展开保证了全局视图，折叠权交给用户。

### 三种模式最终方案

| 模式 | 一屏数量 | 适用 |
|---|---|---|
| **紧凑列表**（默认） | 8~9 | 日常，事件 20 个以内 |
| 舒适列表 | 5~6 | 现状，信息最完整 |
| 分类分组 | 7~8（含分组头） | 事件多、想按类别找 |

设置页自由切换，选择持久化。

## 分组模式下的三个交互约束

### 1. 拖拽只能在组内

分组模式下跨组拖拽意味着改变事件的分类标签，
这是「移动」不是「排序」，语义完全不同。

**约束**：分组模式下拖拽仅限组内，跨组需要进详情页改标签。

### 2. 与分类筛选的关系

分组模式和分类筛选功能重叠但不冲突：

- 筛选：只看某一个分类（过滤掉其他）
- 分组：同时看到所有分类（只是排列方式不同）

两者可共存。但**分组模式下分类筛选意义不大**，
可在该模式下隐藏分类筛选行，减少视觉噪音。

### 3. 新事件的落位

新增或导入的事件追加到末尾，
分组模式下会落到所属分类的最后面——符合预期。

## 决策记录（已与使用者确认）

1. **两种模式起步**：紧凑 / 舒适，设置页自由切换，均可选
2. **分组模式**：纳入本次实施，作为第三种可选模式
3. **宫格模式**：不做（理由见上）
4. **拖拽方式**：先采用**长按拖拽**，实测误触率；
   若误触明显再改为右侧固定手柄
5. **钉选保留**：暂不取消，与手动排序并存
   （钉选 = 置顶层，手动排序 = 组内顺序）

## 待确认

无——方案已确定，可进入 design 与实施。

**唯一遗留观察项**：长按拖拽的误触率需要真机实测才能判断，
实施后请留意「想点开详情却触发了拖拽」的发生频率，
如明显则改用手柄方案。
