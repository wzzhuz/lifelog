# 提取现有实现为 OpenSpec 规范

## 日期

2026-08-31

## 背景

应用在 v1.0.0 已完成开发并产出可用 APK，但需求散落在三份 Markdown 文档
（`docs/需求设计.md`、`docs/技术设计.md`、`docs/使用说明.md`）与大量对话记录中。
这些文档是「叙述式」的，缺少统一的、可被机器校验的行为约定。

带来的具体问题：

1. 后续想调整需求时，AI 助手只能重新读一遍长文档，容易遗漏或误解
2. 文档与代码会逐渐脱节，没人知道哪份是准的
3. 新增功能时没有固定流程，容易直接改代码而跳过需求对齐

## 目标

建立 OpenSpec 规范层，让：

- 系统当前行为有唯一真理源（`openspec/specs/`）
- 后续需求调整走标准 change 流程（`propose → apply → archive`）
- 任何 AI 工具都能按同一套约定工作，不依赖特定的斜杠命令

## 范围

**做**：

- 建立 `openspec/` 目录结构
- 将已完成实现的 7 个核心模块转为 spec 格式
- 编写 `project.md` 项目级约定
- 编写 `AGENTS.md` AI 行为指引

**不做**：

- 不改动任何现有代码或修改应用行为
- 不删除 `docs/` 下的历史文档（保留作为背景材料，但与 spec 冲突时以 spec 为准）
- 不安装 openspec CLI（当前无 Node 环境，且元宝不支持斜杠命令）

## 覆盖的模块

| Spec | 来源 | 覆盖程度 |
|---|---|---|
| `status-calculation` | 需求设计第四章 + 技术设计第四章 | 完整，含三级回退与边界场景 |
| `record-capture` | 需求设计第二、三章 | 完整，含四个摩擦层级 |
| `home-widget` | 需求设计第六章 + 技术设计第五章 | 完整，含 Glance 限制 |
| `data-persistence` | 技术设计第三章 | 完整，含原子写入与滚动备份 |
| `event-management` | 需求设计第三章 | 核心行为 |
| `timeline-review` | 需求设计第三章 P2 | 核心行为 |
| `backup-restore` | 需求设计第三章 P0 | 核心行为 |

## 未覆盖

以下部分仍只在 `docs/` 中，等实际要改时再补 spec：

- 界面视觉细节与配色（Material You 动态取色）
- 预置模板库的具体 24 项清单
- 设置页各项开关的交互细节

**理由**：一次写全会让 spec 变成第二份长文档，反而没人看。
优先覆盖容易改错、改了影响大的模块。
