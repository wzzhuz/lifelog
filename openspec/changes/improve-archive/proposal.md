# 归档：现在是单向黑洞，且性能动机已不成立

## 对应反馈

「归档后的事件在哪查看，是否可以重新启用。是否可以定期把上一年度
或者半年度的记录归档到归档表，这样可以减少首页需要查询的记录数量。」

## 核实结论：两个问题，一个比你说的严重，一个和你以为的不同

### 发现一：归档是单向黑洞（真 bug，比反馈的更严重）

你问「在哪查看、是否可以重新启用」——**答案是：不能，完全没有入口。**

代码现状：

| 位置 | 状态 |
|---|---|
| `DetailScreen.kt:113` | 有「归档」菜单项 ✅ |
| `Repository.archivedEvents()` | 已实现，返回归档事件 ✅ |
| **任何 UI 调用 `archivedEvents()`** | **❌ 一处都没有** |

也就是说：事件一旦归档，就从所有界面消失，
**无法查看、无法恢复、无法删除**。唯一的出路是导出 JSON 手动改字段再导回。

这是我上一轮实现时的疏漏——加了归档的写入路径，忘了给出入口。

### 发现二：归档老记录的**性能动机已经不成立**

你提议归档老记录是出于「减少首页查询量」。
这个理由在 JSON 时代完全正确，但**换到 Room 之后不再适用**：

首页现在走 SQL 聚合（`COUNT` / `MIN` / `MAX`），
**一次 GROUP BY 就拿到每个事件的统计值，不读取任何记录行**。

| 记录总数 | 首页渲染开销 |
|---|---|
| 10 条 | 基本相同 |
| 10,000 条 | 基本相同 |

换句话说：**现在归档 1 万条老记录，首页不会变快哪怕 1 毫秒。**

这个优化的收益是零，但成本不小（要建归档表、迁移数据、
年度回顾要跨两张表查、导出导入要合并）。

## 所以需要先确认一件事

**你想归档，到底是为了什么？**

| 如果动机是 | 建议 |
|---|---|
| 首页性能 | **不需要做**。已经用聚合查询解决了 |
| 首页太乱，想藏掉不用的事件 | 做「事件归档」，但要能查看和恢复 |
| 详情页时间线太长（某事件记录了几百次） | 这个真实存在，但影响很小 |
| 想按年份整理历史 | 年度回顾已经只查该年区间 |

## 无论动机是什么，都要先修的 bug

### 1. 设置页加「已归档」入口

- 列出所有归档事件
- 每条支持「恢复」（取消归档）
- 支持彻底删除（连带记录，需二次确认）

### 2. 归档前给出提示

现在点「归档」是直接生效、且没有任何提示说明后果。
改为弹确认框，写明「归档后可在设置页恢复」。

## 关于「记录归档」的初步判断

**暂不建议做**，理由：

1. 性能收益为零（聚合查询已解决）
2. 会破坏「年度回顾看全部」——你说过只有年度回顾需要看全部，
   而归档恰恰会让年度回顾需要跨表查询，反而变复杂
3. 增加数据模型复杂度，导出导入都要改

**但有一个更轻的替代方案**能达成类似目的：
详情页时间线改为**分页加载**（默认显示最近 20 条，下拉加载更多）。
这样既不改变数据模型，又解决了「一个事件几百条记录一次加载」的问题。

## 不做什么

- ❌ 不做自动定期归档（定时任务在移动端不可靠，且收益为零）
- ❌ 不建独立的归档记录表（除非你确认有别的动机）
- ❌ 不做归档记录的自动清理

## 影响范围
