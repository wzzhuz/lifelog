### 存储方案：从 JSON 迁移到 Room

> ⚠️ **本节记录的是已废弃的初版选型，保留作为决策背景。**
> 当前行为以 `openspec/specs/data-persistence/spec.md` 为准。

**初版选择 JSON 全量文件的理由**：个人生活琐事数据量小，
全量读写性能够用，且省掉注解处理器（KSP），
能显著降低 CI 首次编译的失败概率（本项目无法本地预编译，
GitHub Actions 是唯一的试错场）。

**这个理由后来被证伪**，不是因为数据量，而是两个结构性缺陷：

1. **写入开销随数据量线性增长**
   每记一笔都要重新序列化整个文件并落盘。
   记一笔这样最高频的操作，开销却取决于历史积累了多少数据。

2. **首页给每个事件都装配完整记录列表**
   哪怕界面上只是要显示「共几次」。
   这是比换数据库本身更大的浪费。

3. **搜索需要遍历**
   关键词搜索要在全量记录上做匹配，记录越多越慢。

**迁移后的做法**：

| 场景 | 做法 | 开销 |
|---|---|---|
| 首页列表 | SQL 聚合 `COUNT`/`MIN`/`MAX` | 与记录总数**无关** |
| 详情页时间线 | 分页加载，首屏 20 条 | 与记录总数无关 |
| 详情页统计 | 聚合查询，不依赖已加载记录 | 与记录总数无关 |
| 搜索 | SQL LIKE，带防抖 | 数据库侧完成 |

引入 KSP 确实增加了 CI 编译复杂度（曾因 KSP 版本号格式变更导致首次编译失败——
KSP 从 2.3.0 起不再与 Kotlin 版本绑定，
旧的 `2.3.21-2.0.2` 这种 artifact 已不存在）。
权衡下来，运行时的性能收益值得这点构建期的代价。

### 为什么不用 Coil / Glide

这些图片库会传递引入 OkHttp，给应用带来不必要的网络相关依赖，
与「零网络权限」的设计原则冲突。照片加载用 `BitmapFactory` 直接实现，只有几十行。

### 为什么不用 Hilt / Koin

本项目只有两三个对象需要共享。
（注：Room 已经引入了 KSP，所以「省掉注解处理器」这个理由对 Hilt/Koin 不再成立，
但 ServiceLocator 依然更简单直接——三个对象的依赖图不值得一套框架。）

## 二、数据模型

```kotlin
data class Event(
    val id: Long = 0L,
    val name: String,
    val emoji: String = "📌",
    val colorArgb: Int,
    val targetDays: Int?,      // null = 无固定节奏，由历史自动判断
    val tag: String?,
    val note: String?,
    val isPinned: Boolean = false,
    val isArchived: Boolean = false,
    val sortOrder: Int = 0,
    val createdAt: Long
)

data class Record(
    val id: Long = 0L,
    val eventId: Long = 0L,
    val timestamp: Long,       // 事件发生时间，可倒填
    val note: String?,
    val photoName: String?,    // 应用私有目录下的文件名
    val loggedAt: Long         // 实际录入时间，与 timestamp 区分
)

enum class Freshness { NONE, FRESH, SOON, DUE }

data class EventStatus(
    val event: Event,
    val records: List<Record>,
    val lastTimestamp: Long?,
    val daysSince: Int?,
    val avgGapMillis: Long?,
    val baselineDays: Int,
    val freshness: Freshness,
    val ratio: Float,
    val predictedNextMillis: Long?
)
```

`EventStatus` 是「事件 + 派生状态」的组合，UI 层直接消费，不再自己算。

## 三、持久化

> ⚠️ **本节部分内容已过时。**
> 主存储已改为 Room，JSON 仅用于导出/导入。
> 当前约定见 `openspec/specs/data-persistence/spec.md`。

### 当前：Room（SQLite）

数据库文件位于应用私有目录，版本 2。

| 表 | 说明 |
|---|---|
| `events` | 事件；含 `sortOrder` 与 `sortInGroup` 两个排序字段 |
| `records` | 记录；外键 `eventId`，删除事件时 `ON DELETE CASCADE` |

**两个排序字段为什么要分开**：列表模式的排序是「全局顺序」，
分组模式是「先按标签分组、组内再排」，语义不同。
共用一个字段时，在分组里拖一下会把全局顺序重写成按标签排列的完整顺序。

索引服务于高频查询：`records(eventId, timestamp)`、
`records(timestamp)`、`events(name)`、`events(tag)`。

### 分页与统计

详情页只加载最近 20 条，但统计信息仍基于全量：

| 统计项 | 做法 |
|---|---|
| 累计次数 | `COUNT(*)` |
| 平均间隔 | `(MAX - MIN) / (COUNT - 1)` |

**平均间隔为什么能用首末差**：相邻间隔之和 = 末次 − 首次，
除以间隔个数即得均值，一次聚合就能拿到，不需要逐条两两计算。

⚠️ 统计值**不得**用 `records.size`（已加载数）代替——
那会让「累计次数」随用户点「加载更多」而跳变。

### 曾经：JSON 全量文件（已废弃）

初版位置 `filesDir/lifelog.json`，结构如下：

```
{
  "version": 1,
  "exportedAt": 1234567890,
  "app": "com.zwz.lifelog",
  "events": [ ... ],
  "records": [ ... ]
}
```

写入安全做得是对的，这部分设计被保留下来用于**导出文件的写盘**：

```kotlin
tmpFile.writeText(json)
if (tmpFile.length() > 0) {
    file.delete()
    tmpFile.renameTo(file)     // renameTo 在同一分区是原子操作
}
```

现在 JSON 只承担两个职责：

- **导出/导入**：格式与旧版保持一致，便于外部工具处理
- **备份**：每次修改后维护 `filesDir/backups/` 下最多 4 份滚动备份

### 照片

`filesDir/photos/`，保存时压缩到长边 1600px、JPEG 质量 85%。
备份打包成 zip 时包含 `photos/` 目录。

## 四、状态计算

`StatusCalculator.compute()` 是纯函数，输入事件 + 记录列表，输出 `EventStatus`。

```kotlin
val last = recordsAsc.lastOrNull()?.timestamp
if (last == null) return EventStatus(freshness = NONE, ...)

val d = daysSince(last, now)
val baseline = event.targetDays
    ?: (avg / DAY)                  // 历史平均
    ?: 30f                          // 兜底
val ratio = d / baseline.coerceAtLeast(1f)

freshness = when {
    ratio >= 1f    -> DUE
    ratio >= 0.75f -> SOON
    else           -> FRESH
}
predictedNext = last + (baseline * DAY_MILLIS)
```

纯函数意味着好测试、好推理，不会因为 UI 状态而出现歧义。

## 五、小组件实现

### Glance 的限制

Glance 不是完整的 Compose —— 只有 Glance 提供的 Composable 可用，
不支持 `LazyColumn`、自定义绘制、复杂动画等。
因此小组件内刻意只用了 `Column` / `Row` / `Text` / `Spacer` 这几个最基础的组件，
避免用到不支持的 API 导致运行时崩溃。

### 列表型

`ListWidget` 加载最多 5 个事件（钉选优先 → 最久没做优先），点击打开主界面。

### 单事件型

`SingleWidget` 用 `PreferencesGlanceStateDefinition` 保存绑定的 eventId：
- 添加时通过 `SingleWidgetConfigActivity` 让用户选择事件
- 点击时启动 `QuickRecordActivity` 静默记录

`QuickRecordActivity` 主题设为 `Theme.Translucent.NoTitleBar`，
`onCreate` 里直接起协程写数据然后 `finish()`，
全程不加载任何 Compose UI，所以点下去是「秒记秒退」，没有界面闪烁。

### 刷新时机

`WidgetRefresh.request(context)` 向两个 Receiver 发广播。
调用点：主界面 `onStop`、详情页/列表页每次数据变更。

## 六、CI/CD

文件：`.github/workflows/build.yml`

### Job 1：build（每次 push / PR / 手动触发）

1. `actions/checkout@v4`
2. `actions/setup-java@v4`（Temurin JDK 17）
3. `gradle/actions/setup-gradle@v4`（依赖缓存）
4. 校验 `app/debug.keystore` 存在
5. `./gradlew assembleDebug`
6. 上传 APK 产物（保留 90 天）
7. 输出 SHA256 与文件大小到 Actions 摘要

### Job 2：release（打 `v*` tag 时）

下载 Job 1 的产物，用 `softprops/action-gh-release@v2` 创建 Release 并附上 APK。

### 关键设计：debug 签名一致性

**问题**：GitHub Actions 每次都是全新环境，Gradle 会重新生成 debug 签名密钥。
第二次编译出的 APK 签名与第一次不同，**装不上，必须先卸载（数据全丢）**。

**解决**：把一份固定的 `app/debug.keystore` 提交进仓库，
在 `app/build.gradle.kts` 中显式让 debug 构建使用这份签名：

```kotlin
signingConfigs {
    create("commonDebug") {
        storeFile = file("debug.keystore")
        storePassword = "lifelog2026"
        keyAlias = "lifelogdebug"
        keyPassword = "lifelog2026"
    }
}
buildTypes {
    debug { signingConfig = signingConfigs.getByName("commonDebug") }
    release { signingConfig = signingConfigs.getByName("commonDebug") }  // 未配 release 密钥时兜底
}
```

debug 签名密钥不含任何敏感信息，开源项目中提交它是通行做法。
这样每次 CI 产出的 APK 签名一致，可以直接覆盖升级。

### release 签名

签名配置按优先级解析：**环境变量 > keystore.properties > 回退 debug 签名**

**环境变量方式（CI 用）**

```kotlin
fun signingValue(propKey: String, envKey: String): String =
    System.getenv(envKey)?.takeIf { it.isNotBlank() }
        ?: keystoreProps.getProperty(propKey)?.takeIf { it.isNotBlank() }
        ?: ""
```

四个环境变量：`LIFELOG_KEYSTORE_FILE`、`LIFELOG_STORE_PASSWORD`、
`LIFELOG_KEY_ALIAS`、`LIFELOG_KEY_PASSWORD`。

CI 里把密钥以 base64 存进 Secrets（`RELEASE_KEYSTORE_BASE64`），
运行时解码成临时文件再指过来，密钥不进仓库。

**keystore.properties（本地用）**

项目根目录放 `keystore.properties`（已在 .gitignore 中）：

```properties
storeFile=release.keystore
storePassword=xxx
keyAlias=xxx
keyPassword=xxx
```

**回退到 debug 签名**

两者都没配时，release 构建会用仓库内的 `debug.keystore`。
功能正常，但该密钥公开在仓库里，任何人都能签出同名同签名的包。
**自用无妨，对外分发前请配置专用密钥。**

### 两个 workflow 的分工

| 文件 | 触发 | 产物 | 用途 |
|---|---|---|---|
| `build.yml` | push / PR / 手动 | debug APK | 日常开发验证 |
| `release.yml` | 仅手动 | release APK（+ 可选 AAB） | 对外分发、打 tag 发布 |

### R8 混淆

默认关闭。`GlanceAppWidgetReceiver` 靠反射实例化，
虽然 `proguard-rules.pro` 里保留了相关类，但 Glance 内部还有更多反射路径，
开启后小组件有崩溃风险。个人自用应用体积不是瓶颈，稳定性优先。

需要开启时：`gradle assembleRelease -PminifyRelease=true`，
或在 Release workflow 勾选「开启混淆」。

## 八、已知限制

1. **首次编译可能需要迭代**：依赖版本冲突、Compose 编译器版本不匹配等很常见，
   一般需要 1-3 轮才能跑出第一个可用 APK。这是没有本地编译环境的正常代价。
2. **小组件刷新依赖系统调度**：部分国产 ROM 会限制后台广播，
   可能导致桌面天数更新不及时。打开一次应用即可强制刷新。
3. **无云同步**：数据只在本机。换手机需要手动导出 ZIP 备份再导入。
4. **Glance 1.1.1 不支持自定义字体和复杂布局**：小组件视觉相对朴素。
